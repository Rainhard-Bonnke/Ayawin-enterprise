# Ayawin ERP: plain-language module review

Review date: 19 October 2026. This is a source-code and workflow review, not a legal, accounting, tax, or security certification. A menu item is not proof that a business process is complete. Validate the workflows below with Ayawin's store, sales, procurement, finance, HR, and management users before production use.

## How to read this review

- **Available** means the repository has a working screen and API for the named task; it does not mean every edge case is covered.
- **Partial** means an important step, control, exception, or reconciliation is missing.
- **Not connected** means there is no live external service behind the screen or API shape.
- Every posted business document should have a source record, a user and timestamp, a clear status, and a way to trace its stock or accounting effects.

## Important cross-module risks found in code

These affect correctness, so they come before visual polish:

1. Sales VAT now uses each saleable item's standard, zero-rated or exempt tax group, effective-dated VAT rate and invoice/order tax date. The applied code, treatment, rate and tax amount are stored per document line. The ERP still does not determine the legal tax point from delivery/payment events, calculate beverage excise, apply VAT input-recovery rules to purchases, or submit/reconcile eTIMS returns. Accounts must review product classifications and tax dates before live use.
2. Sales delivery, customer invoice, customer receipt, supplier goods receipt, supplier bill, supplier payment and payroll posting now create/post the general-ledger journal within the same database transaction as the source document. New supplier receipt accruals use account 2150 and matched bills clear the liability account credited by that receipt's journal. Supplier bills already posted under the former double-AP logic need accountant-approved reconciliation. A posting error should roll the operation back. Other posting paths still need this audit; the change has not yet been verified with database integration scenarios.
3. Sales orders reserve stock inside the confirmation transaction after locking the stock balance. Delivery consumes the matching order-line reservation; other stock issues respect reservations; order cancellation releases remaining quantities. These new transaction paths still need database scenarios before production use.
4. Bank statement lines match only posted journal lines on the selected 11xx account, within 14 days and to the cent. The statement closing amount is checked against imported movements, and unmatched book lines are listed. The workflow does not yet prove full bank-versus-GL balance equality; book entries such as bank charges must be recorded before matching. Treat a completed statement as a matched statement, not as a full bank-control reconciliation.
5. Lot tracking is opt-in. Existing stock can be reconciled into opening lots by a user with approval permission; the action requires lot quantities and extended costs to match the existing on-hand quantity and valuation, preserves the stock total, and is audited. Tracked receipts require batch and future expiry; issues allocate unexpired lots FEFO; transfers and material returns preserve lot identity. Positive stock adjustment supports one batch per item variance, so count variances spanning multiple lots need to be split in a future update. Positive driver stocktake, lot-specific reservations, quarantine, supplier return and recall workflows remain incomplete. Apply migration 032 before using these paths.
6. One invoice payment currently allocates to one invoice. The ERP has receipt-allocation records, but user-facing payment-on-account and allocation across multiple invoices are not implemented.
7. The UI permission check is only a convenience. Every action still needs server-side permission, tenant, branch and document-state validation. Review those together for each mutation.

## How users should understand the main workflows

**Buy goods:** internal request → approval → supplier PO → count delivery into a GRN → resolve shortages/damage → supplier invoice match → approve bill → payment → bank reconciliation. A PO is the promise to buy; a GRN is what physically arrived; a supplier bill is what the supplier asks to be paid. Keep those as different records so mismatches are visible.

**Sell goods:** quote/order → credit and available-stock check → reserve → pick/dispatch → customer proof of delivery → tax invoice → collection → bank reconciliation. A dispatch reduces stock; an invoice creates a customer debt; a receipt reduces that debt. They are different events.

**Handle a customer return:** open the posted invoice and its linked delivery → select the returned delivery/batch quantity and mark it good or damaged → prepare a credit-note draft with a reason and date → a different authorized user posts it. Posting reverses the invoice's sales and output VAT; good goods return to sellable stock, while damaged goods enter quarantine; inventory and COGS reverse using the original delivery issue cost. The amount applied reduces the invoice receivable; a cash refund of excess requires a bank/cash account and payment reference, then posts a separate refund journal in the same transaction. Drafts reserve quantities so they cannot be credited twice. Credits cannot yet be allocated across multiple invoices, and direct KRA eTIMS transmission is not connected.

**Count stock:** create a scoped count → record physical quantities → investigate differences → independent approval → post adjustment → reconcile stock value to the GL. Never silently overwrite the balance; preserve the count and adjustment history.

**Close a month:** finish operational posting → reconcile stock, AR/AP, cash/bank, tax and payroll controls → review trial balance and exceptions → approve period close. A closed period should not accept backdated posting without an explicit controlled reopen.

## Research and design references

- KRA says businesses must onboard eTIMS and issue electronic tax invoices; direct ERP-to-KRA use of OSCU/VSCU requires development, testing and certification. Treat a stored reference or mock response as not connected until KRA accepts a real submission. [KRA eTIMS overview](https://www.kra.go.ke/online-services/etims), [KRA system-to-system integration](https://www.kra.go.ke/business/etims-electronic-tax-invoice-management-system/learn-about-etims/etims-system-to-system-integration)
- KRA VAT guidance identifies standard, zero-rated and exempt treatment and says VAT return/payment is due by the 20th of the following month. Keep rules configurable and verify the current treatment for the actual products and taxpayer. [KRA VAT](https://www.kra.go.ke/individual/filing-paying/types-of-taxes/value-added-tax)
- KRA's input-tax guidance says deductions depend on VAT registration, taxable business use and valid electronic tax documentation. The current supplier-bill workflow does not yet validate all of these conditions, so accounts must review purchase-tax claims. [KRA input-tax deduction guidance](https://www.kra.go.ke/helping-tax-payers/faqs/understanding-vat-input-tax-deduction)
- KRA's current guidance says PAYE returns are due by the 9th of the following month. Keep statutory rules effective-dated and payroll records reviewable. [KRA PAYE due date](https://www.kra.go.ke/component/kra_faq/faq/729)
- Kenya's ODPC describes data-subject access, objection, correction and deletion rights, alongside purpose limitation and data minimization. Admin needs an auditable process for these requests, subject to lawful retention obligations. [ODPC data-subject rights](https://www.odpc.go.ke/rights-of-a-data-subject/)
- Procurement matching should compare billed quantities and prices against both the approved order and what the warehouse actually received. [Microsoft accounts payable invoice matching overview](https://learn.microsoft.com/en-us/dynamics365/finance/accounts-payable/accounts-payable-invoice-matching)
- Confirmed customer/warehouse demand should reserve available stock so another order cannot promise the same units. [Microsoft inventory reservations](https://learn.microsoft.com/en-us/dynamics365/supply-chain/inventory/reserve-inventory-quantities)
- Bank reconciliation should compare imported statement lines with ERP payments and receipts, using review for ambiguous matches. [Microsoft bank reconciliation](https://learn.microsoft.com/en-us/dynamics365/finance/cash-bank-management/reconcile-bank-statements-advanced-bank-reconciliation)
- For lot tracking, use source/destination identities and recorded traceability events, not just a batch-number text box. [GS1 Global Traceability Standard](https://www.gs1.org/standards/gs1-global-traceability-standard/current-standard)
- For stock valuation, validate the chosen costing policy and write-down process with an accountant against [IAS 2 Inventories](https://www.ifrs.org/issued-standards/list-of-standards/ias-2-inventories/).

## Delivery sequence

1. Repair accounting consistency and tax configuration in sales, purchases and collections.
2. Complete inventory traceability: lots, reservations, FEFO, quarantine, transit, counts and valuation reconciliation.
3. Complete customer/supplier returns, credits, allocations, aging and collection/payment approvals.
4. Finish bank-versus-GL reconciliation, then add financial close controls.
5. Complete employee lifecycle, payroll approvals and statutory remittance evidence.
6. Finish fixed-asset lifecycle, master-data controls, privacy and branch scoping.
7. Add certified/live integrations and operational AI with evidence, human approval, retry and reconciliation.

Deliver one stage at a time. For each stage, agree a small set of real business scenarios, opening balances and expected accounting entries with the Ayawin process owner; only then enable the workflow for live posting.
